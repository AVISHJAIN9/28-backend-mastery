# WebAuthn & Passkeys - Deep Dive Theory

## Overview

WebAuthn (Web Authentication) is a W3C standard that enables cryptographic login without passwords. Passkeys are user-friendly implementations of WebAuthn that use biometrics (face/fingerprint) or hardware security keys.

**Key Insight:** Instead of storing passwords, you store the user's *public key*. Only their device (with private key) can prove they own the account.

## The Evolution of Authentication

```
Phase 1: Plaintext Passwords (1960s-1990s)
  ✗ Passwords stored as-is, easily hacked

Phase 2: Hashed Passwords (1990s-2000s)
  ⚠️ Passwords hashed, but still subject to brute force

Phase 3: Salted + Bcrypt (2000s-2010s)
  ✓ Passwords salted and hashed, much slower to crack

Phase 4: Multi-Factor Auth (2010s)
  ✓✓ Password + second factor (SMS, TOTP, security key)

Phase 5: Passwordless / Passkeys (2020s+)
  ✓✓✓ No passwords at all, cryptographic proof of identity
```

## How WebAuthn Works: Registration & Authentication

### Registration Flow (10 Steps)

```
Step 1: User clicks "Sign up with Passkey"
        ↓
Step 2: Server generates random CHALLENGE (32 bytes)
        ↓
Step 3: Server sends challenge to browser
        ↓
Step 4: Browser shows biometric prompt (Face ID / Fingerprint)
        ↓
Step 5: User authenticates (face/fingerprint scan)
        ↓
Step 6: Device generates KEY PAIR:
        • Private Key (stored secretly on device)
        • Public Key (sent to server)
        ↓
Step 7: Device signs challenge with private key
        ↓
Step 8: Browser sends signed data + public key to server
        ↓
Step 9: Server verifies signature using public key
        ↓
Step 10: Server stores public key, user is registered
```

### Authentication Flow (10 Steps)

```
Step 1: User clicks "Sign in with Passkey"
        ↓
Step 2: Server generates new random CHALLENGE
        ↓
Step 3: Browser shows biometric prompt again
        ↓
Step 4: User authenticates (face/fingerprint)
        ↓
Step 5: Device signs challenge with STORED private key
        ↓
Step 6: Browser sends signed challenge to server
        ↓
Step 7: Server verifies signature using stored public key
        ↓
Step 8: ✓ User is authenticated (no password needed)
        ↓
Step 9: Server generates JWT tokens
        ↓
Step 10: User can access protected routes
```

## Public Key Cryptography Explained

### Traditional Password Auth (Vulnerable)

```
User → "password123" → Server checks hash("password123") == stored_hash
Problem: If server is hacked, hashes can be cracked with rainbow tables
Average time to crack: 1-3 days per password
```

### WebAuthn Auth (Secure)

```
Device generates:
  Private Key (secret, never leaves device)
  Public Key (safe to share with server)

Registration:
  Device: "Here's my public key" 
  Server: "I'll store this"

Login:
  Server: "Sign this challenge with your private key"
  Device: signature = privateKey.sign(challenge)
  Server: "Is this signature valid with the public key?"
  Server: publicKey.verify(challenge, signature) → ✓ YES

Why secure:
  - Private key never leaves device
  - Each challenge is unique (no replay attacks)
  - Signature can only be created by device with private key
  - No password database to hack
```

## Key WebAuthn Concepts

### 1. Challenge

- Random 32-byte value generated by server
- Unique for each registration/authentication
- Expires after 5-10 minutes if not used
- Prevents replay attacks (attacker can't reuse old signature)

```javascript
challenge = crypto.randomBytes(32).toString('base64url')
// Example: "F8Ys_xp-7c3-K5x9..." (base64url encoded)
```

### 2. Relying Party (RP)

- Your server/application
- Identified by domain name (example.com)
- WebAuthn binds credential to this origin
- Attacker at attacker.com can't use credential even if stolen

```javascript
rp = {
  name: "My App",
  id: "example.com"  // CRITICAL: Must match current origin
}
```

### 3. User Entity

- Information about user being registered
- userID: Unique internal identifier (NOT email)
- name: Username or email
- displayName: Human-readable name

```javascript
user = {
  id: "fc2a3e7d-1b8f-4d2a-9c5e-8b1a2f3e4d5f",  // UUID
  name: "alice@example.com",
  displayName: "Alice Smith"
}
```

### 4. Authenticator Types

**Platform Authenticators (Built-in):**
- Face ID (iOS, macOS, Windows Hello)
- Fingerprint (Android, Windows)
- Native to device, always available

**Cross-Platform Authenticators (Hardware):**
- YubiKey, Google Titan, Hyper Fido
- USB or NFC connection
- More portable, highly secure

### 5. Counter (Clone Detection)

- Signature counter maintained by authenticator
- Increments on each use
- If counter doesn't increase → possible key cloning
- Backward counter → authentication rejected

## Security: Attack Prevention

### Attack 1: Database Breach

**Traditional Auth:**
```
Attacker hacks server database:
  Stolen: email + password_hash
  Attack: Crack hashes with GPU cluster (1000s per second)
  Result: ✗ Attacker gains access to thousands of accounts
```

**WebAuthn:**
```
Attacker hacks server database:
  Stolen: email + public_key
  Attack: Try to use public key to authenticate?
  Result: ✓ Public key is useless without private key (stays on device)
```

### Attack 2: Phishing

**Traditional Auth:**
```
User visits fake.example.com (phishing site)
User enters password
Attacker captures password → can login as them
Result: ✗ ACCOUNT COMPLETELY COMPROMISED
```

**WebAuthn:**
```
User visits fake.example.com (phishing site)
Server requests signature
Device: "Sign for fake.example.com?"
↓
Device checks credential origin binding
↓
Credential only valid for example.com, not fake.example.com
Device: REJECTED (refuses to sign)
Result: ✓ LOGIN FAILED (phishing prevented by cryptography)
```

### Attack 3: Man-in-the-Middle (MITM)

**Traditional Auth:**
```
Attacker intercepts HTTPS connection
  Captures password → can re-use it for future logins
  Problem: Password is the same every time
```

**WebAuthn:**
```
Attacker intercepts signature
  Has signature for challenge X
  But next login uses different challenge Y
  Old signature invalid for new challenge
  Problem: Signature tied to specific challenge
Result: ✓ ATTACK PREVENTED (replay-attack proof)
```

### Attack 4: Credential Theft

**Traditional Auth:**
```
Browser malware steals password from memory
  Password written to disk/clipboard
  Problem: Password stored in multiple places
```

**WebAuthn:**
```
Device: Private key = Hardware-bound, never exposed
  Even if malware runs on device, private key stays secure
  Biometric required each time (liveness check)
Result: ✓ MUCH MORE DIFFICULT (hardware security)
```

## WebAuthn Registration: Deep Dive

### Browser API Call

```javascript
// User clicks "Register with Passkey"
const credential = await navigator.credentials.create({
  publicKey: {
    challenge: new Uint8Array(32),        // Server-sent challenge
    rp: { 
      name: "My App", 
      id: "example.com"                   // CRITICAL: Domain binding
    },
    user: {
      id: new Uint8Array(16),             // UUID
      name: "alice@example.com",
      displayName: "Alice Smith"
    },
    pubKeyCredParams: [
      { alg: -7, type: "public-key" }     // ES256 (P-256)
    ],
    authenticatorSelection: {
      authenticatorAttachment: "platform", // Use Face ID/Touch ID
      userVerification: "preferred"        // Biometric preferred
    },
    attestation: "none"                   // Don't require attestation
  }
});

// Device generates key pair, shows biometric prompt
// User scans face/fingerprint
// Device signs challenge with private key
// Browser returns credential object
```

### Server-Side Validation

```javascript
// Verify signature on server
const publicKeyObj = parsePublicKey(credential.publicKey);
const isValid = publicKeyObj.verify(
  challenge,
  credential.signature
);

if (!isValid) {
  return res.status(401).json({ error: 'Signature invalid' });
}

// Store public key for future logins
await db.credentials.insert({
  userId: user.id,
  credentialId: credential.id,
  publicKey: credential.publicKey,      // Store this!
  counter: credential.counter,
  createdAt: new Date()
});
```

## WebAuthn Authentication: Deep Dive

### Browser API Call

```javascript
// User clicks "Sign in with Passkey"
const assertion = await navigator.credentials.get({
  publicKey: {
    challenge: new Uint8Array(32),      // NEW challenge from server
    timeout: 60000,
    userVerification: "preferred"
  }
});

// Device shows biometric prompt
// User scans face/fingerprint
// Device signs challenge with STORED private key
// Browser returns assertion object
```

### Server-Side Validation

```javascript
// Find stored public key
const credential = await db.credentials.findOne({ id: assertionCredentialId });
if (!credential) {
  return res.status(401).json({ error: 'Credential not found' });
}

// Verify signature with stored public key
const isValid = credential.publicKey.verify(
  challenge,
  assertion.signature
);

if (!isValid) {
  return res.status(401).json({ error: 'Authentication failed' });
}

// Check counter (clone detection)
if (assertion.counter <= credential.counter) {
  return res.status(400).json({ error: 'Possible key cloning detected' });
}

// Update counter
await db.credentials.update(
  { id: credential.id },
  { counter: assertion.counter, lastUsed: new Date() }
);

// Generate JWT tokens
const token = jwt.sign(
  { userId: user.id, email: user.email },
  JWT_SECRET,
  { expiresIn: '7d' }
);

res.json({ accessToken: token, user });
```

## Implementation Best Practices

1. **Always HTTPS**
   - WebAuthn requires secure context
   - Will fail on HTTP (except localhost for dev)

2. **Domain Binding (RP_ID)**
   - Must match your actual domain
   - Prevents cross-site credential usage
   - Phishing prevention mechanism

3. **Challenge Uniqueness**
   - Use `crypto.randomBytes(32)`
   - Never reuse challenge
   - Clear expired challenges (5-minute TTL)

4. **Counter Validation**
   - Increment expected on each auth
   - Detect key cloning
   - Log suspicious activity

5. **Backup Codes**
   - Generate during registration
   - Stored separately (hashed)
   - Allow account recovery if device lost

6. **Error Messages**
   - Don't leak user existence
   - Don't reveal what failed (fingerprint? network? device?)
   - Generic: "Authentication failed"
