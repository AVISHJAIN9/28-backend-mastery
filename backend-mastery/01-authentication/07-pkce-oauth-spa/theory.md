# PKCE OAuth SPA - Deep Dive Theory

## Overview

**PKCE** (Proof Key for Code Exchange, pronounced "pixy") is an extension to OAuth 2.0 defined in [RFC 7636](https://tools.ietf.org/html/rfc7636) that adds an extra layer of security to the Authorization Code flow. It was designed specifically to address security vulnerabilities in public clients like Single-Page Applications (SPAs), mobile apps, and desktop applications that cannot securely store client secrets.

### The Problem PKCE Solves

Traditional OAuth 2.0 Authorization Code flow has a critical weakness for public clients:

```
Traditional Flow:
1. Client redirects to OAuth provider
2. User logs in and authorizes
3. Provider returns authorization code
4. Client exchanges code + client_secret for token
   
DANGER: In SPAs, client_secret is visible in JavaScript!
```

An attacker can:
- Intercept the authorization code during redirect
- Use a different app with same credentials
- Inject malicious JavaScript to steal credentials
- Perform authorization code substitution attacks

### The PKCE Solution

Add a cryptographic proof that only the original client can provide:

```
PKCE Flow:
1. Client generates random code_verifier
2. Client creates code_challenge from verifier
3. Client includes code_challenge in authorize request
4. Provider returns authorization code
5. Client exchanges code + code_verifier for token
6. Provider verifies: SHA256(verifier) == challenge
   
BENEFIT: Attacker has code but not verifier!
```

## Architecture

### Components

1. **OAuth Client**: Your SPA (e.g., React app)
2. **Authorization Server**: OAuth provider (Google, GitHub, etc.)
3. **Resource Server**: API with protected resources
4. **Code Verifier**: Random cryptographic string generated by client
5. **Code Challenge**: SHA256 hash of verifier, sent to server
6. **Authorization Code**: Temporary credential from server
7. **Access Token**: Used to access protected resources

## Security Model

### Why Code Verifier Protection Works

The key insight: **An attacker can intercept the authorization code, but not the code verifier.**

```javascript
// What's sent to OAuth server in Step 2:
{
  code_challenge: "E9Mrozoa36-ZUbVxWNZ-76dxq1xJJp1wbZsVMNJPW38"
  // Only hash is exposed!
}

// What's sent in Step 4:
{
  code_verifier: "jVBbHAL6s7ghnRZhv5pVQ8J2mZ8qLkW3pN9wX2Y3Z4aBc-Def_Ghi..." 
  // Original value, but cannot be reverse-engineered from hash
}

// Attacker Problem:
if (attacker_has_code) {
  // Has: authorization code
  // Needs: code_verifier to exchange
  // Can't compute: original verifier from challenge hash (SHA256 is one-way)
}
```

### Threat Model Protection

#### Attack: Authorization Code Interception

**Threat**: Attacker intercepts authorization code during redirect

```
Attacker: I have the code, let me exchange it!
Server: Sure, but what's your code_verifier?
Attacker: Uh... I don't have it
Server: ✗ Denied
```

**Protection**: Code is worthless without verifier; verifier is only in original client's memory.

#### Attack: Authorization Code Substitution

**Threat**: Malicious app tries to use legitimate client's code

```
Malicious App:
  Step 1: Generate its own verifier_A and challenge_A
  Step 2: Request auth code (using legitimate client's client_id)
  Step 3: Get code with challenge_A
  
  Now tries to exchange:
  Step 4: POST /token with code + its verifier_A
  Server: Checking... SHA256(verifier_A) != challenge_A
  Server: ✗ Denied
```

**Protection**: Every code is bound to specific code_challenge; only generating client knows verifier.

#### Attack: MITM Credential Theft

**Threat**: Man-in-the-middle intercepts code or credentials

```
Secure: HTTPS encrypts the channel
But even if HTTPS broken:
- Authorization code alone is useless (need verifier)
- Code verifier never sent in plaintext during authorize step
- Verifier stays in client memory during exchange
```

**Protection**: Multi-factor proof - need both knowledge (verifier) and proof (challenge match).

## Implementation Details

### 1. Code Verifier Generation

Requirements (per RFC 7636):
- **Length**: 43-128 characters
- **Character Set**: `[a-zA-Z0-9-._~]`
- **Uniqueness**: Random, cryptographically secure
- **Entropy**: Minimum 43 octets (32 bytes of entropy)

```javascript
// Correct implementation
function generateCodeVerifier() {
  const chars = 'ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789-._~';
  let verifier = '';
  
  // Use crypto for secure randomness
  const randomValues = new Uint8Array(128);
  crypto.getRandomValues(randomValues);
  
  for (let i = 0; i < 128; i++) {
    verifier += chars[randomValues[i] % chars.length];
  }
  
  return verifier;
}

// Example output
// "jVBbHAL6s7ghnRZhv5pVQ8J2mZ8qLkW3pN9wX2Y3Z4aBc-Def_GhiJklMnOpQrStUvWxYzAb0cDeF1gHiJkLmNoPq"
```

### 2. Code Challenge Generation

Requirements:
- **Method**: SHA256 (default, required for SPAs)
- **Encoding**: Base64URL (not standard Base64!)
- **One-way**: Use cryptographic hash

```javascript
// Correct implementation
async function generateCodeChallenge(verifier) {
  // Step 1: Hash the verifier using SHA256
  const encoder = new TextEncoder();
  const buffer = encoder.encode(verifier);
  const hashBuffer = await crypto.subtle.digest('SHA-256', buffer);
  
  // Step 2: Convert to Base64URL (not standard Base64)
  const hashArray = Array.from(new Uint8Array(hashBuffer));
  const hashString = String.fromCharCode(...hashArray);
  const hash = btoa(hashString);
  
  // Step 3: Replace Base64 chars with Base64URL chars
  const challenge = hash
    .replace(/\+/g, '-')  // + → -
    .replace(/\//g, '_')  // / → _
    .replace(/=/g, '');   // Remove =
  
  return challenge;
}

// Example transformation
// SHA256 output (bytes):     [196, 245, 31, 173, ...]
// Base64:                    xPUfrQ==
// Base64URL:                 xPUfrQ
```

**Why Base64URL?**
- Standard Base64 uses `+/=` characters
- Base64URL uses `-_` instead
- Required for safe transmission in URLs and JSON

### 3. Authorization Code Flow

```javascript
// Client side
async function requestAuthorizationCode() {
  // Step 1: Generate & store verifier
  const verifier = generateCodeVerifier();
  sessionStorage.setItem('code_verifier', verifier);
  
  // Step 2: Generate challenge
  const challenge = await generateCodeChallenge(verifier);
  
  // Step 3: Request auth code from server
  const response = await fetch('/auth/authorize', {
    method: 'POST',
    body: JSON.stringify({
      code_challenge: challenge,
      redirect_uri: window.location.origin
    })
  });
  
  // Server stores: { code, code_challenge, expiry, used: false }
}
```

### 4. Token Exchange Flow

```javascript
// Client side
async function exchangeCodeForToken(authCode) {
  // Step 1: Retrieve stored verifier
  const verifier = sessionStorage.getItem('code_verifier');
  
  // Step 2: Exchange code for token
  const response = await fetch('/auth/token', {
    method: 'POST',
    body: JSON.stringify({
      code: authCode,
      code_verifier: verifier,  // Original value sent here
      redirect_uri: window.location.origin
    })
  });
  
  // Server validates: SHA256(verifier) == stored_challenge
  // Server returns: access_token, refresh_token, etc.
}
```

### 5. Server-Side Validation

```javascript
// Server side - Node.js example
const crypto = require('crypto');

function validatePKCEChallenge(receivedVerifier, storedChallenge) {
  // Recompute challenge from received verifier
  const hash = crypto
    .createHash('sha256')
    .update(receivedVerifier)
    .digest();
  
  const computed = Buffer.from(hash)
    .toString('base64')
    .replace(/\+/g, '-')
    .replace(/\//g, '_')
    .replace(/=/g, '');
  
  // Constant-time comparison (prevent timing attacks)
  return crypto.timingSafeEqual(
    Buffer.from(computed),
    Buffer.from(storedChallenge)
  );
}
```

## Comparison with Other Methods

### PKCE vs Basic Auth
```javascript
// Basic Auth - User details sent every request
Authorization: Basic base64(username:password)

// PKCE - Tokens prove identity without credentials
Authorization: Bearer access_token_jwt
```

**Why PKCE wins**: 
- Credentials never sent after login
- Tokens can be scoped and revoked
- User can't accidentally expose password
- Credentials can be invalidated server-side

### PKCE vs OAuth (No PKCE)
```javascript
// OAuth without PKCE - Vulnerable
// Attacker intercepts code → Can exchange directly (has client_secret)

// OAuth with PKCE - Protected
// Attacker intercepts code → Can't exchange (doesn't have verifier)
```

### PKCE vs Implicit Flow (Deprecated)
```javascript
// Implicit Flow - Token directly in URL fragment risks
https://app.com#access_token=eyJ0eXAi...

// PKCE Flow - Code in URL, token in secure response
https://app.com?code=abc123 → exchange for token internally
```

**Why PKCE replaced Implicit**:
- No access token in URL (not logged in browser history)
- More steps = harder to attack
- Proper refresh token support
- Works with modern SPA requirements

## Scalability

### Server-Side Considerations

1. **Authorization Code Storage**
   - Short-lived (10 minutes)
   - Stores: `{ code, code_challenge, redirect_uri, expiresAt, used }`
   - Can use in-memory Map, Redis, or database
   - Clean up expired codes periodically

2. **Token Blacklist (for Logout)**
   - Store revoked tokens
   - Check on every protected request
   - Use Redis with TTL matching token expiry
   - Or database with indexed expiresAt

3. **Rate Limiting**
   - Limit authorization requests: 10/minute per IP
   - Limit token exchanges: 5/minute per code
   - Prevent code reuse attacks (automatic on exchange)

### Client-Side Considerations

1. **Code Verifier Storage**
   - sessionStorage (cleared on tab close) - SAFER
   - localStorage (persists across sessions) - RISKY
   - Memory variable (lost on page reload) - FRAGILE
   - **Recommendation**: sessionStorage

2. **Token Storage**
   - Memory (lost on refresh) - SAFEST
   - sessionStorage (XSS vulnerability) - OKAY
   - localStorage (XSS vulnerability) - RISKY
   - HttpOnly cookie (CSRF protection needed) - BEST

### Load Balancing
```
For clustered deployments:

Option 1: Sticky Sessions
- Code + challenge stored in request.session
- Route user to same server for exchange

Option 2: Central Store
- Use Redis for authorization codes
- All servers can verify and exchange
- Better failure handling

Option 3: Signed Tokens
- Server signs authorization code
- Any server can decrypt and validate
- No persistent storage needed
```

## Real-World Attack Scenarios

### Scenario 1: Malware in Browser
```
Attacker's goal: Steal access token

How PKCE helps:
- Malware can intercept authorization code
- But code alone is useless (needs verifier)
- Verifier is in app's JavaScript memory
- Malware would need to inject before auth (hard)
- Defense: Use HttpOnly for final token storage
```

### Scenario 2: Compromised Network
```
Attacker's goal: Capture credentials during auth

How PKCE helps:
- User never sends password after initial OAuth
- No secrets transmitted except in HTTPS body
- Challenge is public (can't leak sensitive info)
- Verifier never sent during authorize step
- Even if MITM, verifier != challenge (useless)
```

### Scenario 3: Phishing Attack
```
Attacker's goal: Trick user to evil.com, steal tokens

How PKCE helps:
- User authenticates on real OAuth provider (not attacker's site)
- Code alone can't be used without verifier
- Attacker's app won't have verifier for legitimate code
- Redirect URI mismatch detected
```

## Summary

**PKCE** is the modern standard for SPA authentication because it:

1. ✅ Eliminates need for client secrets
2. ✅ Prevents authorization code interception attacks
3. ✅ Works with third-party OAuth providers
4. ✅ Complies with security best practices
5. ✅ Supported by all major OAuth providers
6. ✅ Simple to implement correctly
7. ✅ Required by major providers (Google, GitHub, etc.)

**When to use PKCE**:
- Single Page Applications (SPAs) - React, Vue, Angular
- Mobile applications - iOS, Android
- Desktop applications - Electron, native apps
- Any public client without backend secrets

**When NOT to use PKCE**:
- Never. PKCE is safe to use everywhere and is now standard even with client secrets
