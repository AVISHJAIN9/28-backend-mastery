📧 Module 02: Email Queuing & Async Retry

Queue-based email sending with exponential backoff, dead letter queues, and bounce handling

📚 Overview

This module teaches production-grade email queue management. Instead of sending emails directly (synchronously), we queue them for background processing with intelligent retry logic, bounce handling, and monitoring.

Key Concepts

  • Queue - Temporary storage for email jobs waiting to be sent
  • Producer - Application that adds emails to the queue
  • Consumer - Background worker that processes the queue
  • Priority - Critical emails processed before low-priority ones
  • Retry Strategy - Rule for when/how to retry failed emails
  • Backoff - Increasing delay between retries (exponential, linear, fixed)
  • Dead Letter Queue (DLQ) - Storage for permanently failed emails
  • Bounce - Email delivery failure reported by ISP

✨ Features

⚡ Fast Queuing

Add emails instantly without waiting for SMTP. Response in ~5ms instead of 500ms-5s.

🔄 Smart Retries

Exponential backoff retries: 5s → 10s → 20s → 40s → ... Intelligent failure handling.

💀 Dead Letter Queue

Permanently failed emails stored for manual review instead of being deleted.

📬 Bounce Handling

Track hard bounces, soft bounces, complaints. Suppress invalid addresses.

🎯 Priority Processing

Critical emails (password resets, alerts) sent before newsletters.

📊 Monitoring

Real-time queue statistics, job tracking, health metrics.

🛡️ Rate Limiting

Protect downstream email providers from overload.

🔍 Audit Logging

Complete history of all email operations for compliance.

🔄 Job States & Transitions

State Description Next States
queued Waiting in queue to be sent processing, deadletter
processing Currently being sent sent, failed, deadletter
sent Successfully delivered to SMTP bounced (if bounce received)
failed Failed, waiting for retry queued (retry), deadletter
deadletter Permanently failed, manual review needed queued (manual retry)
bounced Bounce reported by ISP suppressed (hard bounce)

⚙️ Retry Strategies

Exponential Backoff

Formula: delay = baseDelay × 2^(attempts)

Example: 5s → 10s → 20s → 40s → 80s

Use Case: General failures, temporary issues. Gives server more recovery time.

Linear Backoff

Formula: delay = baseDelay × attempts

Example: 5s → 10s → 15s → 20s → 25s

Use Case: Rate limiting, API quota issues. Steady pressure instead of exponential.

Fixed Delay

Formula: delay = baseDelay

Example: 5s → 5s → 5s → 5s → 5s

Use Case: Quick retries, transient network glitches. Keep it simple.

🎯 Pre-configured Strategies

Strategy Max Attempts Base Delay Backoff Type Use Case
Aggressive 10 1 second Exponential Critical emails (password resets, alerts, payments)
Moderate 5 5 seconds Exponential Standard transactional (welcome, confirmations)
Conservative 3 1 minute Linear Bulk emails, newsletters, low-priority

⚠️ Error Handling

Bounce Types

Type Cause Action
Hard Bounce Invalid email address, user doesn't exist Block email forever, move to suppression list
Soft Bounce Mailbox full, server temporarily down Retry later with longer delays
Complaint User marked as spam Block email, investigate complaint
⚡ Important: Hard bounces are permanent. Never retry. Each retry damages your sender reputation.

🔄 Example: End-to-End Flow

Step 1: User Registration

POST /api/queue/add
{
  "recipientEmail": "alice@example.com",
  "subject": "Welcome to MyApp!",
  "body": "<h1>Welcome</h1>",
  "priority": 10,
  "maxAttempts": 5,
  "backoffStrategy": "exponential"
}

Response:
{
  "success": true,
  "job": {
    "id": 1,
    "status": "queued",
    "nextRetry": null
  }
}

Step 2: Process Queue

POST /api/queue/process

// Server attempts to send email
// SMTP server is temporarily down → Connection timeout
// Email send fails

Response:
{
  "success": true,
  "processed": 1,
  "results": [{
    "id": 1,
    "status": "failed",
    "attempt": 1,
    "nextRetry": "2024-01-01T10:00:05Z",  // 5 seconds later
    "reason": "ECONNREFUSED"
  }]
}

Step 3: Automatic Retry

5 seconds later, system retries automatically...

POST /api/queue/process

// SMTP server is now up, email sends successfully

Response:
{
  "success": true,
  "processed": 1,
  "results": [{
    "id": 1,
    "status": "sent",
    "sentAt": "2024-01-01T10:00:05Z"
  }]
}

Step 4: Hard Bounce Received

Email provider reports the address is invalid...

POST /api/bounces/webhook
{
  "email": "alice@example.com",
  "bounceType": "hard_bounce",
  "bounceSubType": "permanent"
}

// System:
// 1. Logs the bounce
// 2. Moves any queued emails to alice@example.com to DLQ
// 3. Marks address as suppressed

Step 5: View Dead Letter Queue (if needed)

GET /api/dlq/items

Response:
{
  "count": 1,
  "items": [{
    "id": 1,
    "recipientEmail": "alice@example.com",
    "reason": "Hard bounce received",
    "movedAt": "2024-01-01T10:00:10Z"
  }]
}

🏗️ Architecture

┌──────────────┐
│  Request     │  Queue email
│  Handler     │──────────────→ Queue Storage
└──────────────┘               (In-Memory/Redis)
                                      ↓
                            ┌─────────┴─────────┐
                            │                   │
                     ┌─ Status: queued
                     │  ┌─ Status: processing
                     │  ├─ Retry logic
                     │  └─ Backoff delays
                     │
            ┌────────┤  ┌─ Status: sent (success)
            │        │  │
     Queue  │        └─ Status: failed
   Processor│           Retry with backoff
            │
            │        ┌──────────────────┐
            ├──────→ │ SMTP Provider    │
            │        │ (Nodemailer,SES) │
            │        └──────────────────┘
            │                │
            └────────┬───────┘
                     │
        ┌─ Success ──┤
        │            └─ Bounce
        │                │
        ▼                ▼
    Job: sent      Job: bounced
                   + Log bounce
                   + Block email
                   + Move to DLQ
