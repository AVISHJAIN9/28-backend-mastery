📱 Device Token Registration Flow

1. Client App requests device token from FCM (or subscribes to Web Push) 2. Client receives token/subscription endpoint 3. Client sends token to backend: POST /api/devices/register { "platform": "fcm", "token": "cNf4pT7sL9mKx3bQ6vY2aZ8wH1jE5gR4tU0dP3oN6sL" } 4. Backend validates token format based on platform - FCM: Must be 100+ characters - Web Push: Must include endpoint URL + keys 5. Backend checks for duplicates (upsert) - If token exists: Update lastUsedAt timestamp - If new: Create new device record 6. Return device ID to client { "deviceId": "device_1001", "status": "active" } 7. Client stores device ID for future use

🔐 VAPID Keys for Web Push

VAPID (Voluntary Application Server Identification) is a security protocol that proves you're authorized to send Web Push notifications.

What are VAPID Keys?

Key Type Purpose Use Case
Public Key Shared with push service; client uses to encrypt data Given to client/browser; included in Web App Manifest
Private Key Used by server to sign VAPID token; proves identity Kept secret on server; never shared with client

Encryption Flow (Web Push)

1. Browser requests push permission 2. Browser subscribes to push service (e.g., Firebase) - Receives: endpoint URL, p256dh key, auth key 3. Browser sends subscription to app server 4. Server wants to send notification 5. Server creates VAPID "authentication header" - Signs with private key - Includes public key in header - Push service verifies signature 6. Server encrypts payload with p256dh (browser's public key) 7. Server sends to push service: - Encrypted payload - VAPID authentication header 8. Push service forwards to browser 9. Browser decrypts with p256dh (private key) 10. Browser displays notification

📤 Notification Sending - Single vs Batch

Single Device Notification

POST /api/notifications/send
Request: 
{
  "deviceId": "device_1001",
  "title": "Order Shipped",
  "body": "Your order #12345 has shipped!",
  "data": {
    "orderId": "12345",
    "trackingUrl": "https://track.example.com/12345"
  }
}
Response: 
{
  "notificationId": "notif_1001",
  "status": "sent",
  "deviceId": "device_1001",
  "deliveredAt": "2024-03-20T15:30:01Z"
}

Batch Notification (Up to 1000 devices)

POST /api/notifications/batch
Request: 
{
  "deviceIds": [
    "device_1001",
    "device_1002",
    "device_1003",
    ... (up to 1000)
  ],
  "title": "New Feature Available",
  "body": "Check out our new chat feature!"
}
Response: 
{
  "message": "Batch notifications sent",
  "sent": 3,
  "failed": 0,
  "notificationIds": [
    "notif_1001",
    "notif_1002",
    "notif_1003"
  ]
}

📊 Rate Limiting

Endpoint Limit Window Purpose
POST /devices/register 50 requests 1 hour Prevent token spam
POST /notifications/send 100 requests 15 minutes Prevent notification spam to single devices
POST /notifications/batch 10 requests 1 hour Prevent bulk notification abuse
Note: Rate limits are per-user (by JWT token). Exceeding limits returns HTTP 429 Too Many Requests.

Aspect Firebase Cloud Messaging (FCM) Web Push API

⚠️ Error Handling

Common Error Codes

Code Status Meaning How to Fix
INVALID_TOKEN 401 JWT expired or invalid Regenerate JWT token
INVALID_FCM_TOKEN 400 FCM token format wrong Verify token from Firebase SDK
INVALID_ENDPOINT 400 Web Push endpoint missing Include subscription.endpoint
DEVICE_NOT_FOUND 404 Device doesn't exist Register device first
TITLE_TOO_LONG 400 Title > 200 chars Shorten title to ≤200 chars
BODY_TOO_LONG 400 Body > 4000 chars Shorten body to ≤4000 chars
TOO_MANY_REQUESTS 429 Rate limit exceeded Wait before retrying

📈 Real-World Examples

E-Commerce: Order Notifications

Scenario: Send order status updates to customer's devices 
// When order ships
POST /api/notifications/send
{
  "deviceId": "device_user_123",
  "title": "Order Shipped!",
  "body": "Your order #12345 is on its way",
  "data": {
    "orderId": "12345",
    "trackingUrl": "https://track.example.com/12345",
    "estimatedDelivery": "2024-03-25"
  }
}
Benefits: Customer gets instant notification, can click to track shipment

Social Network: Friend Requests

Scenario: Notify user's friends about follow request 
// Get friend's devices
const friendDevices = await getDevicesByUserId(friendId);
const deviceIds = friendDevices.map(d => d.deviceId);

// Send batch notification
POST /api/notifications/batch
{
  "deviceIds": deviceIds,
  "title": "New Follow Request",
  "body": "Alice wants to follow you!",
  "data": {
    "requesterId": "user_alice",
    "action": "accept"
  }
}
Benefits: Scales to notify thousands instantly

Messaging App: Chat Alerts

Scenario: Alert user about new messages 
// Only if user is not actively using app
if (userAppStatus !== 'active') {
  POST /api/notifications/send
  {
    "deviceId": device_id,

🧪 Testing Checklist

Device Registration

  • [ ] Register FCM device token (100+ chars)
  • [ ] Register Web Push subscription (with endpoint + keys)
  • [ ] Verify duplicate tokens are ignored (upsert)
  • [ ] Test invalid token formats are rejected
  • [ ] Verify registered device appears in /api/devices list

Notification Sending

  • [ ] Send notification to single device
  • [ ] Verify notification appears in logs (status: 'sent')
  • [ ] Send batch to 10 devices
  • [ ] Send batch to 100 devices
  • [ ] Send batch to 1000 devices (max limit)
  • [ ] Test batch with >1000 devices (should fail)

Payload Validation

  • [ ] Test title at exactly 200 chars (should pass)
  • [ ] Test title at 201 chars (should fail)
  • [ ] Test body at exactly 4000 chars (should pass)
  • [ ] Test body at 4001 chars (should fail)
  • [ ] Send with data object (should include in notification)

Rate Limiting

  • [ ] Register device 49 times in 1 hour (should pass)
  • [ ] Register device 51st time in 1 hour (should get 429)
  • [ ] Send 100 single notifications in 15 min (should pass)
  • [ ] Send 101st notification in same 15 min (should get 429)
  • [ ] Send 10 batch notifications in 1 hour (should pass)

Engagement Tracking

  • [ ] Track notification as clicked
  • [ ] Verify /api/stats shows engagement rate
  • [ ] Verify delivery rate calculated correctly
  • [ ] Check notification logs show clickedAt timestamp

⚡ Performance Tips

  • Batch operations: Use batch endpoint for >10 devices (more efficient)
  • Payload size: Keep under 4KB; compress images/data
  • Token management: Refresh tokens every 90 days
  • Dead token cleanup: Remove tokens that fail 3+ times
  • Rate limiting: Adjust limits based on your user tier pricing
  • Monitoring: Track delivery/failure rates daily

🔒 Security Best Practices

  • JWT Secret: Use strong secret (32+ chars), rotate regularly
  • VAPID Private Key: Never expose to client; store securely
  • HTTPS Only: Web Push requires HTTPS (not HTTP)
  • Token Validation: Always verify token format and ownership
  • Rate Limiting: Prevents malicious users from spamming
  • Data Encryption: Sensitive data in notifications should be encrypted
