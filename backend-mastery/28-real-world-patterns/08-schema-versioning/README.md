# Module 08: Schema Versioning - Complete Guide\n\n## Overview\n\nDatabase schema evolution without downtime. This module covers:\n\n- **Schema Versioning** - Track and manage schema changes\n- **Data Alignment** - Transform data between schema versions\n- **Zero-Downtime Migrations** - Apply changes safely\n- **Rollback Capability** - Revert breaking changes\n- **Compatibility Checking** - Validate schema compatibility\n- **Migration History** - Complete audit trail\n\n## Architecture\n\n```\n┌─────────────────────────────────────┐\n│ React Frontend (port 3000)          │\n├─────────────────────────────────────┤\n│ Create / Align / Rollback / Query   │\n└────────┬────────────────────────────┘\n         │ HTTP/JSON\n         ↓\n┌─────────────────────────────────────┐\n│ Express.js (port 4008)              │\n├─────────────────────────────────────┤\n│ ├─ GET  /api/secure/schema          │\n│ ├─ POST /api/secure/schema/create   │\n│ ├─ POST /api/secure/schema/align    │\n│ ├─ POST /api/secure/schema/rollback │\n│ └─ GET  /api/secure/schema/history  │\n└────────┬────────────────────────────┘\n         │ In-Memory DB\n         ↓\n┌─────────────────────────────────────┐\n│ Schema Registry & Versions          │\n├─────────────────────────────────────┤\n│ ├─ Collection Schemas               │\n│ ├─ Version History                  │\n│ ├─ Migration Log                    │\n│ └─ Adapter Registry                 │\n└─────────────────────────────────────┘\n```\n\n## API Endpoints\n\n### 1. Get Current Schema\n**Endpoint:** `GET /api/secure/schema?collection_name=users&version=1.0.0`\n\nRetrieve a specific or current schema version.\n\n**Response:**\n```json\n{\n  \"success\": true,\n  \"collection_name\": \"users\",\n  \"version\": \"1.0.0\",\n  \"schema\": {\n    \"id\": \"integer\",\n    \"name\": \"string\",\n    \"email\": \"string\"\n  },\n  \"migration_type\": \"add_field\",\n  \"created_at\": \"2024-01-15T10:00:00Z\"\n}\n```\n\n---\n\n### 2. Create Schema Version\n**Endpoint:** `POST /api/secure/schema/create`\n\nCreate a new schema version for a collection.\n\n**Request:**\n```json\n{\n  \"version\": \"1.1.0\",\n  \"collection_name\": \"users\",\n  \"schema\": {\n    \"id\": \"integer\",\n    \"name\": \"string\",\n    \"email\": \"string\",\n    \"phone\": \"string\"\n  },\n  \"migration_type\": \"add_field\",\n  \"changes\": {\n    \"added\": [\"phone\"]\n  },\n  \"description\": \"Add phone field to users\",\n  \"zero_downtime\": true\n}\n```\n\n**Response:**\n```json\n{\n  \"success\": true,\n  \"message\": \"Schema version 1.1.0 created\",\n  \"schema\": {\n    \"version\": \"1.1.0\",\n    \"collection_name\": \"users\",\n    \"migration_type\": \"add_field\",\n    \"created_at\": \"2024-01-15T10:05:00Z\",\n    \"previous_version\": \"1.0.0\",\n    \"rollback_supported\": true\n  }\n}\n```\n\n---\n\n### 3. Align Data to New Schema\n**Endpoint:** `POST /api/secure/schema/align-data`\n\nTransform data from old schema to new schema.\n\n**Request:**\n```json\n{\n  \"from_version\": \"1.0.0\",\n  \"to_version\": \"1.1.0\",\n  \"collection_name\": \"users\",\n  \"batch_size\": 1000,\n  \"dry_run\": true\n}\n```\n\n**Response (Simulated):**\n```json\n{\n  \"success\": true,\n  \"message\": \"Data would be aligned to schema 1.1.0\",\n  \"alignment\": {\n    \"from_version\": \"1.0.0\",\n    \"to_version\": \"1.1.0\",\n    \"total_records\": 5234,\n    \"processed_batches\": 6,\n    \"status\": \"simulated\"\n  }\n}\n```\n\n---\n\n### 4. Rollback Schema\n**Endpoint:** `POST /api/secure/schema/rollback`\n\nRollback to a previous schema version.\n\n**Request:**\n```json\n{\n  \"collection_name\": \"users\",\n  \"to_version\": \"1.0.0\",\n  \"verify_before_rollback\": true\n}\n```\n\n**Response:**\n```json\n{\n  \"success\": true,\n  \"message\": \"Rolled back to schema version 1.0.0\",\n  \"current_version\": \"1.0.0\",\n  \"collection_name\": \"users\"\n}\n```\n\n---\n\n### 5. Check Schema Compatibility\n**Endpoint:** `GET /api/secure/schema/check-compatibility?from_version=1.0.0&to_version=1.1.0&collection_name=users`\n\nDetermine if schemas are compatible.\n\n**Response:**\n```json\n{\n  \"success\": true,\n  \"compatible\": true,\n  \"from_version\": \"1.0.0\",\n  \"to_version\": \"1.1.0\",\n  \"message\": \"Schemas are compatible\"\n}\n```\n\n---\n\n### 6. Get Migration History\n**Endpoint:** `GET /api/secure/schema/migration-history?collection_name=users&limit=20`\n\nView schema migration audit trail.\n\n**Response:**\n```json\n{\n  \"success\": true,\n  \"collection_name\": \"users\",\n  \"total_migrations\": 3,\n  \"history\": [\n    {\n      \"timestamp\": \"2024-01-15T10:05:00Z\",\n      \"version\": \"1.1.0\",\n      \"migration_type\": \"add_field\",\n      \"status\": \"created\",\n      \"zero_downtime\": true\n    },\n    {\n      \"timestamp\": \"2024-01-15T10:10:00Z\",\n      \"version\": \"1.1.0\",\n      \"action\": \"data_aligned\",\n      \"status\": \"success\"\n    }\n  ]\n}\n```\n\n---\n\n## Real-World Examples\n\n### Example 1: Adding an Optional Field (Zero-Downtime)\n```bash\n# Step 1: Create new schema 1.0.0: Initial schema\n   - 1.1.0: Add optional field\n   - 2.0.0: Breaking change\n\n3. **Enable zero-downtime for non-breaking changes**\n   - Remove fields\n   - Rename columns\n   - Add optional fields\n\n4. **Validate compatibility**\n   - Check between all involved versions\n   - Plan data transformation\n   - Test on staging first\n\n5. **Monitor migration progress**\n   - Track batch processing\n   - Log transformation errors\n   - Measure total time\n\n---\n\n## Migration Patterns\n\n### Pattern 1: Add Optional Field\n```json\n{\n  \"migration_type\": \"add_field\",\n  \"changes\": {\n    \"added\": [\"new_field\"]\n  },\n  \"zero_downtime\": true,\n  \"schema\": {\n    \"new_field\": \"type (optional)\"\n  }\n}\n```\n\n### Pattern 2: Remove Field\n```json\n{\n  \"migration_type\": \"remove_field\",\n  \"changes\": {\n    \"removed\": [\"old_field\"]\n  },\n  \"zero_downtime\": true\n}\n```\n\n### Pattern 3: Rename Field\n```json\n{\n  \"migration_type\": \"rename_field\",\n  \"changes\": {\n    \"renamed\": {\n      \"old_name\": \"new_name\"\n    }\n  },\n  \"zero_downtime\": true\n}\n```\n\n### Pattern 4: Change Field Type\n```json\n{\n  \"migration_type\": \"change_type\",\n  \"changes\": {\n    \"field\": \"email\",\n    \"from\": \"string\",\n    \"to\": \"string (indexed)\"\n  },\n  \"zero_downtime\": true\n}\n```\n\n### Pattern 5: Breaking Change\n```json\n{\n  \"migration_type\": \"breaking\",\n  \"changes\": {\n    \"removed\": [\"field1\", \"field2\"],\n    \"renamed\": {\"old\": \"new\"},\n    \"added\": [\"required_field\"]\n  },\n  \"zero_downtime\": false,\n  \"description\": \"Major schema restructure\"\n}\n```\n\n---\n\n## Troubleshooting\n\n### Issue: Rollback Failed\n**Solution:** Check if rollback is supported for breaking changes\n\n### Issue: Schema Incompatibility\n**Solution:** Use data alignment to transform records\n\n### Issue: Migration Taking Too Long\n**Solution:** Reduce batch_size to avoid blocking, increase for speed\n\n---\n\nSee `theory.md` for production migration patterns and `setup.md` for complete setup guide.
