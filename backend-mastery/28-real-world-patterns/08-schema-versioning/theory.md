name: \"Alice\",\n  email: \"alice@example.com\"\n};\n\n// New requirement: Add phone field (v1.1.0)\nconst users = {\n  id: 1,\n  name: \"Alice\",\n  email: \"alice@example.com\",\n  phone: \"555-1234\"  // NEW\n};\n\n// Challenge: Database has MILLIONS of records\n// Can't afford 10-minute downtime per deployment\n```\n\n### Downtime Impact Calculation\n\n```\nUsers online: 10,000\nDowntime: 10 minutes\nLost transactions: ~10,000 × 10 min = 100,000 actions\nRevenue impact: $10,000+ depending on business model\n```\n\n---\n\n## Evolution of Schema Management\n\n### Phase 1: Manual SQL (Pre-2000)\n```sql\n-- HUGE DOWNTIME: Locks table\nALTER TABLE users ADD COLUMN phone VARCHAR(20);\n\n-- Problems:\n-- - Locks table\n-- - Requires downtime\n-- - No rollback\n-- - No version control\n```\n\n### Phase 2: Migration Scripts (2000-2010)\n```ruby\n# Rails migrations approach\nclass AddPhoneToUsers < ActiveRecord::Migration\n  def up\n    add_column :users, :phone, :string\n  end\n  \n  def down\n    remove_column :users, :phone\n  end\nend\n\n# Improvements:\n# - Version controlled\n# - Reversible\n# - Automated\n# - Still locks table\n```\n\n### Phase 3: Online Schema Changes (2010-2015)\n```javascript\n// Using tools like Percona PT-Online-Schema-Change\n// Key insight: Create shadow table, migrate data, swap\n// - Still some blocking\n// - Better than direct ALTER\n```\n\n### Phase 4: Dual-Write Pattern (2015-Present)\n```javascript\n// Write to both old and new schema\n// Migrate data gradually\n// Switch readers\n// No downtime\n\n┌─────────────────────┐\n│ Request Handler     │\n└──────────┬──────────┘\n           │ Writes to BOTH\n           ↓\n     ┌──────────────┐\n     │ Old Schema   │\n     │ (users v1)   │\n     └──────────────┘\n     \n     ┌──────────────┐\n     │ New Schema   │  ← Simultaneously\n     │ (users v2)   │\n     └──────────────┘\n```\n\n---\n\n## Schema Versioning Strategies\n\n### Strategy 1: Expand-Then-Contract Pattern\n\n```\nPhase 1: EXPAND\n┌──────────────┐\n│ users (v1)   │\n├──────────────┤\n│ id           │\n│ name         │\n│ email        │\n│ phone (NEW)  │ ← Add column\n└──────────────┘\n\nPhase 2: MIGRATE\n├─ Write to both\n├─ Copy data slowly\n├─ Update readers\n└─ Verify correctness\n\nPhase 3: CONTRACT\n┌──────────────┐\n│ users (v2)   │\n├──────────────┤\n│ id           │\n│ name         │\n│ email        │\n│ phone        │ ← Now required\n└──────────────┘\n```\n\n### Strategy 2: Shadow Schema Pattern\n\n```\n┌─────────────────────────────────────────┐\n│       Live Traffic (v1.0.0)             │\n├─────────────────────────────────────────┤\n│                                         │\n│  users (LIVE)      users_v2 (SHADOW)   │\n│  ┌──────────────┐  ┌──────────────┐   │\n│  │ id           │  │ id           │   │\n│  │ name         │  │ first_name   │   │\n│  │ email        │  │ last_name    │   │\n│  │ phone        │  │ email        │   │\n│  │              │  │ phone        │   │\n│  └──────────────┘  └──────────────┘   │\n│        ↑                   ↑            │\n│        │ Single write      │            │\n│        └──────→ Replicate──┘            │\n│                                         │\n│  Readers: Still on users (v1.0.0)      │\n│  Writers: users + users_v2 (dual)      │\n└─────────────────────────────────────────┘\n\nPhase 2: Switch Readers\n├─ Validate all data copied\n├─ Gradually switch readers to v2\n├─ Monitor for issues\n└─ Complete cutover\n```\n\n### Strategy 3: Versioned API Pattern\n\n```javascript\n// Different API versions for different schema versions\n\n// API v1 reads/writes old schema\napp.get('/v1/users/:id', (req, res) => {\n  const user = getUser(req.params.id);  // OLD SCHEMA\n  res.json({\n    id: user.id,\n    name: user.name,\n    email: user.email\n  });\n});\n\n// API v2 uses new schema\napp.get('/v2/users/:id', (req, res) => {\n  const user = getUser(req.params.id);  // NEW SCHEMA\n  res.json({\n    id: user.id,\n    firstName: user.first_name,\n    lastName: user.last_name,\n    email: user.email\n  });\n});\n\n// Gradually migrate clients from v1 to v2\n```\n\n---\n\n## Zero-Downtime Migration Patterns\n\n### Pattern: Add Optional Field\n\n```javascript\n// Step 1: Add column with DEFAULT or NULL\nALTER TABLE users ADD COLUMN phone VARCHAR(20) DEFAULT NULL;\n// Time: Minimal, no data migration\n// Downtime: <1ms\n\n// Step 2: Populate data gradually\nUPDATE users SET phone = extract_phone() \n  WHERE phone IS NULL\n  LIMIT 1000;  // Batch to avoid locking\n// Can run during business hours\n// Doesn't block readers\n\n// Step 3: Switch application logic\n// Old app: ignores phone\n// New app: reads/writes phone\n// Both work simultaneously\n\n// Step 4: Clean up\n// Remove DEFAULT NULL after all data populated\n// This is phase out of v1\n```\n\n### Pattern: Remove Field\n\n```javascript\n// Step 1: Stop writing to field\n// Old code: writes to both\n// New code: only writes to keep field\napp.post('/users', (req, res) => {\n  db.users.insert({\n    id: req.body.id,\n    name: req.body.name,\n    email: req.body.email\n    // deprecated_field: NOT written anymore\n  });\n});\n\n// Step 2: Stop reading field\n// App doesn't need it anymore\napp.get('/users/:id', (req, res) => {\n  const user = db.users.findById(req.params.id);\n  res.json({\n    id: user.id,\n    name: user.name,\n    email: user.email\n    // deprecated_field: NOT returned anymore\n  });\n});\n\n// Step 3: After monitoring (days/weeks)\n// Delete column\nALTER TABLE users DROP COLUMN deprecated_field;\n```\n\n### Pattern: Rename Field\n\n```javascript\n// Step 1: Add new column\nALTER TABLE users ADD COLUMN \n  first_name VARCHAR(100);\n\n// Step 2: Dual-write pattern\napp.post('/users', (req, res) => {\n  db.users.insert({\n    name: req.body.name,        // OLD\n    first_name: req.body.name   // NEW - DUAL\n  });\n});\n\n// Step 3: Migrate existing data\nUPDATE users SET first_name = name;  // BATCH\n\n// Step 4: Dual-read pattern\napp.get('/users/:id', (req, res) => {\n  const user = db.users.findById(req.params.id);\n  // Return whichever is available\n  const firstName = user.first_name || user.name;\n  res.json({ firstName });\n});\n\n// Step 5: Drop old column\nALTER TABLE users DROP COLUMN name;\n```\n\n---\n\n## Breaking Changes Management\n\n### Scenario: Complete Schema Restructure\n\n```javascript\n// v1.0.0: Flat structure\nconst user_v1 = {\n  id: 1,\n  first_name: \"John\",\n  last_name: \"Doe\",\n  email: \"john@example.com\"\n};\n\n// v2.0.0: Nested structure (BREAKING)\nconst user_v2 = {\n  id: 1,\n  name: {\n    first: \"John\",\n    last: \"Doe\"\n  },\n  contact: {\n    email: \"john@example.com\"\n  }\n};\n\n// Migration Timeline:\n// Day 1: Create v2 schema alongside v1\n// Days 1-3: Dual-write to both\n// Days 3-7: Copy and verify data\n// Week 2: Gradually switch readers\n// Week 3: Keep v1 as fallback\n// Month 2: Sunset v1 schema\n```\n\n### Safe Breaking Change Workflow\n\n```javascript\nasync function safeMigrationPlan() {\n  // 1. Create new schema\n  await createSchemaVersion({\n    version: '2.0.0',\n    migration_type: 'breaking',\n    zero_downtime: false\n  });\n  \n  // 2. Check compatibility\n  const compat = await checkCompatibility('1.0.0', '2.0.0');\n  if (!compat.compatible) {\n    console.log('Breaking: Full data alignment required');\n  }\n  \n  // 3. Plan data migration\n  const plan = createMigrationPlan('1.0.0', '2.0.0');\n  // {\n  //   transforms: [\n  //     { from: 'first_name', to: 'name.first' },\n  //     { from: 'last_name', to: 'name.last' },\n  //     { from: 'email', to: 'contact.email' }\n  //   ]\n  // }\n  \n  // 4. Test migration on staging\n  const stagingResults = await runMigration(plan, 'staging');\n  if (!stagingResults.success) {\n    console.log('Failed on staging - fix mappings');\n    return;\n  }\n  \n  // 5. Production with fallback\n  try {\n    const prodResults = await runMigration(plan, 'production');\n    if (prodResults.errors.length > threshold) {\n      await rollbackToVersion('1.0.0');\n    }\n  } catch (e) {\n    await rollbackToVersion('1.0.0');\n  }\n}\n```\n\n---\n\n## Data Alignment Algorithms\n\n### Algorithm 1: Batch Transform\n\n```javascript\nasync function batchTransformData(\n  fromSchema, \n  toSchema, \n  batchSize = 1000\n) {\n  let processed = 0;\n  let offset = 0;\n  \n  while (true) {\n    // Get batch\n    const records = db.query(\n      `SELECT * FROM users LIMIT ${batchSize} OFFSET ${offset}`\n    );\n    \n    if (records.length === 0) break;\n    \n    // Transform\n    const transformed = records.map(record => \n      transformRecord(record, fromSchema, toSchema)\n    );\n    \n    // Insert to new schema\n    await db.insertMany('users_v2', transformed);\n    \n    // Log progress\n    processed += records.length;\n    console.log(`Progress: ${processed}/${totalRecords}`);\n    \n    // Avoid CPU spike - small delay\n    await sleep(100);\n    \n    offset += batchSize;\n  }\n}\n```\n\n### Algorithm 2: Shadow Copy with Validation\n\n```javascript\nasync function shadowCopyWithValidation(\n  fromSchema,\n  toSchema,\n  validationRules\n) {\n  const startTime = Date.now();\n  const errors = [];\n  \n  // Copy all records\n  const records = db.query(`SELECT * FROM users`);\n  \n  for (const record of records) {\n    try {\n      const transformed = transformRecord(record);\n      \n      // Validate before inserting\n      const validation = validateRecord(transformed, validationRules);\n      if (!validation.valid) {\n        errors.push({\n          recordId: record.id,\n          errors: validation.errors\n        });\n        continue;\n      }\n      \n      await db.insert('users_v2', transformed);\n    } catch (e) {\n      errors.push({\n        recordId: record.id,\n        error: e.message\n      });\n    }\n  }\n  \n  return {\n    success: errors.length === 0,\n    totalRecords: records.length,\n    errors: errors,\n    duration: Date.now() - startTime\n  };\n}\n```\n\n---\n\n## Real-World Case Studies\n\n### Case Study 1: Stripe's Schema Evolution\n\n**Challenge:** Support multiple API versions (v1, v2, v3) while maintaining single Database\n\n**Solution:**\n```javascript\n// Database stores data in latest format\nconst user = {\n  id: 1,\n  name: { first: 'John', last: 'Doe' },\n  contact: { email: 'john@example.com' }\n};\n\n// Adapters for each API version\nconst v1Adapter = (record) => ({\n  id: record.id,\n  first_name: record.name.first,\n  last_name: record.name.last,\n  email: record.contact.email\n});\n\nconst v2Adapter = (record) => ({\n  id: record.id,\n  person: record.name,\n  email: record.contact.email\n});\n\n// Route handler adapts response\napp.get('/v1/users/:id', (req, res) => {\n  const user = db.users.findById(req.params.id);\n  res.json(v1Adapter(user));\n});\n\napp.get('/v3/users/:id', (req, res) => {\n  const user = db.users.findById(req.params.id);\n  res.json(user);  // Latest schema\n});\n```\n\n**Benefits:**\n- Single source of truth (database)\n- Multiple API versions supported\n- Gradual client migration\n- Easy rollout of breaking changes\n\n### Case Study 2: Pinterest's Zero-Downtime Column Rename\n\n**Scenario:** Rename 500GB table column without downtime\n\n**Approach:**\n1. Create shadow table with new column names\n2. Dual-write to old + new (application level)\n3. Copy existing data in background (parallel jobs)\n4. Switch double-write read path\n5. Keep old table as fallback\n6. After 1 month, drop old table\n\n**Result:** Completed during business hours with no user impact\n\n### Case Study 3: Airbnb's Multi-Version Schema\n\n**Challenge:** Support web, mobile (iOS), mobile (Android), API partners\n\n**Solution:**\n```javascript\nconst schemaVersions = {\n  v1: { /* Legacy format */ },\n  v2: { /* Web 5.0+ */ },\n  v3: { /* Mobile 3.0+ */ },\n  v4: { /* Internal API */ }\n};\n\nconst clients = {\n  'web-5.0': 'v2',\n  'mobile-ios-3.0': 'v3',\n  'mobile-android-2.5': 'v1',\n  'partner-api': 'v4'\n};\n\napp.get('/listings/:id', (req, res) => {\n  const listing = db.listings.findById(req.params.id);\n  const clientVersion = getClientVersion(req);\n  const schemaVersion = clients[clientVersion];\n  const adapter = adapters[schemaVersion];\n  \n  res.json(adapter(listing));\n});\n```\n\n**Key Insight:** Database uses latest schema; different clients get different views\n\n---\n\n## Common Pitfalls\n\n### ❌ Pitfall 1: Single Atomic Migration\n```javascript\n// WRONG: All changes at once\nALTER TABLE users \n  ADD COLUMN phone VARCHAR(20),\n  DROP COLUMN deprecated_field,\n  RENAME COLUMN email_address TO email,\n  MODIFY name VARCHAR(255) NOT NULL;\n  \n// PROBLEMS:\n// - Long lock time\n// - Hard to debug if fails\n// - Can't rollback partially\n// - Risky\n```\n\n**✅ Correct:**\n```javascript\n// Step-by-step\nALTER TABLE users ADD COLUMN phone VARCHAR(20);\n// Verify and wait\n\nALTER TABLE users DROP COLUMN deprecated_field;\n// Verify and wait\n\nALTER TABLE users RENAME COLUMN email_address TO email;\n// And so on...\n```\n\n### ❌ Pitfall 2: No Dual-Write Phase\n```javascript\n// WRONG: Immediate cutover\ndb.schema = 'v2.0.0';\napp.restart();  // Everything breaks\n```\n\n**✅ Correct:**\n```javascript\n// Write to both\nconst record = { /* v1 format */ };\ndb.users_v1.insert(record);\ndb.users_v2.insert(transformToV2(record));\n\n// Read from primary, fall back to old\nconst user = db.users_v2.findById(id) || \n             transformFromV1(db.users_v1.findById(id));\n```\n\n### ❌ Pitfall 3: Assuming All Data Transforms Successfully\n```javascript\n// WRONG\nrecords.forEach(r => {\n  db.insert('new_table', transformData(r));\n  // If transform fails: crash and data loss\n});\n```\n\n**✅ Correct:**\n```javascript\nconst errors = [];\nrecords.forEach(r => {\n  try {\n    const transformed = transformData(r);\n    db.insert('new_table', transformed);\n  } catch (e) {\n    errors.push({ recordId: r.id, error: e });\n  }\n});\n\nif (errors.length > threshold) {\n  rollback();\n  alertTeam(errors);\n}\n```\n\n---\n\n## Summary\n\n**Schema Versioning Key Principles:**\n\n1. **Expand-Contract Pattern** - Add before removing\n2. **Dual-Write Phase** - Write to both old and new\n3. **Gradual Migration** - Don't rush data transformation\n4. **Validation at Each Step** - Catch errors early\n5. **Easy Rollback** - Keep old schema as fallback\n6. **Adapter Pattern** - Transform at API layer\n7. **Version Independence** - Schema version ≠ API version\n8. **Monitor and Alert** - Track migration progress\n\nThis is how industry scales databases without downtime.\n
