# Module 10: Chaos Engineering - Intentional Failure Testing\n\n## Overview\n\nChaos engineering is the practice of intentionally introducing failures into systems to test resilience and discover weaknesses before they cause real outages. By systematically injecting latency, errors, network partitions, and resource exhaustion, teams can verify their systems handle failures gracefully.\n\n## Key Concepts\n\n### Fault Injection\n\nDeliberately introducing faults to observe system behavior:\n\n1. **Latency Injection** - Add delays to service calls\n2. **Error Injection** - Simulate service failures\n3. **Network Partition** - Simulate network failures\n4. **Resource Exhaustion** - Simulate CPU/memory pressure\n\n### Chaos Testing vs Unit Testing\n\n**Unit Tests:**\n```javascript\n// Test happy path\ntest('getUserReturnsUserData', () => {\n  const user = getUser(1);\n  expect(user.name).toBe('Alice');\n});\n```\n\n**Chaos Tests:**\n```javascript\n// Test failure path\ninjectLatency('userService', 5000);  // 5 second delay\nmakeRequest();  // Does system timeout?\n\ninjectError('postService', 'SERVICE_UNAVAILABLE');\nmakeRequest();  // Does system fallback?\n```\n\n### Chaos Scenarios\n\nPre-defined failure patterns that test real-world conditions:\n\n1. **Cascading Failures** - One service failing causes others to fail\n2. **Latency Spike** - All services become slow\n3. **Partial Outage** - Some services unavailable, others working\n4. **Resource Leak** - Memory/CPU gradually consumed\n5. **Network Chaos** - Slow, dropped packets, partitions\n\n## Architecture\n\n```\n┌─────────────────────────────────────┐\n│    Chaos Engineering Controller     │\n├─────────────────────────────────────┤\n│                                     │\n│  • Latency Injection                │\n│  • Error Injection                  │\n│  • Network Partitions               │\n│  • Resource Exhaustion              │\n│  • Chaos Scenarios                  │\n│  • Resilience Testing               │\n│                                     │\n└────────────┬────────────────────────┘\n             │\n       ┌─────v─────┐\n       │ Services  │\n       ├───────────┤\n       │ User      │\n       │ Post      │\n       │ Analytics │\n       └───────────┘\n```\n\n## API Endpoints\n\n### 1. Inject Latency\n\n**Endpoint:** `POST /api/secure/chaos/inject-latency`\n\n**Request:**\n```json\n{\n  \"service_name\": \"userService\",\n  \"latency_ms\": 2000,\n  \"probability\": 0.8,\n  \"duration_seconds\": 30\n}\n```\n\n**Response:**\n```json\n{\n  \"success\": true,\n  \"chaos_id\": \"abc123\",\n  \"message\": \"Latency injection started for userService\",\n  \"configuration\": {\n    \"service_name\": \"userService\",\n    \"latency_ms\": 2000,\n    \"probability\": 0.8,\n    \"duration_seconds\": 30,\n    \"started_at\": \"2024-01-15T10:30:00Z\"\n  }\n}\n```\n\n### 2. Start Small\n\n```javascript\n// ✓ GOOD: Start with low probability\ninjectLatency('userService', 500, 0.1);  // 10% of requests\n\n// ✗ BAD: Too aggressive\ninjectLatency('userService', 5000, 1.0);  // All requests fail\n```\n\n### 2. Test During Low Traffic\n\n```javascript\n// Schedule chaos tests during off-peak hours\n// Business hours: 9 AM - 5 PM = NO chaos tests\n// Off-peak: 10 PM - 6 AM = Run chaos tests\n```\n\n### 3. Monitor Everything\n\n```javascript\n// Before injecting chaos\nbaselineMetrics = getMetrics();\n\n// Inject chaos\ninjectError('userService', 0.5);\n\n// Monitor during chaos\nsetInterval(() => {\n  currentMetrics = getMetrics();\n  if (currentMetrics.error_rate > threshold) {\n    stopChaos();  // Auto-stop if degradation too severe\n  }\n}, 1000);\n```\n\n### 4. Automate Testing\n\n```javascript\n// Run automated chaos tests nightly\nviaCronJob = {\n  schedule: '0 2 * * *',  // 2 AM daily\n  tests: [\n    { scenario: 'latency_spike', intensity: 'low' },\n    { scenario: 'cascading_failures', intensity: 'medium' },\n    { scenario: 'partial_outage', intensity: 'high' }\n  ]\n};\n```\n\n### 5. Document Findings\n\n```javascript\n// After each chaos test, document:\nResults = {\n  test_date: '2024-01-15',\n  scenario: 'cascading_failures',\n  duration_seconds: 60,\n  findings: [\n    'Database connection pool exhausted',\n    'Cache not handling service failures',\n    'Timeout values too long'\n  ],\n  improvements: [\n    'Increase connection pool from 10 to 25',\n    'Implement circuit breaker for cache',\n    'Reduce timeout from 5s to 3s'\n  ]\n};\n```\n\n## Testing Workflow\n\n1. **Baseline Test** - System healthy, establish baseline metrics\n2. **Inject Chaos** - Introduce failures\n3. **Monitor** - Observe system behavior\n4. **Analyze** - Review metrics and logs\n5. **Fix** - Address identified weaknesses\n6. **Verify** - Run same test again\n\n## Implementation Checklist\n\n- [ ] Latency injection mechanism\n- [ ] Error injection mechanism\n- [ ] Network partition simulation\n- [ ] Chaos scenario runners\n- [ ] Resilience testing framework\n- [ ] Metrics collection\n- [ ] Status tracking\n- [ ] Auto-stop on threshold breach\n- [ ] Comprehensive logging\n- [ ] React UI for test control\n\n## Running the Module\n\n```bash\n# Install dependencies\nnpm install\n\n# Start backend server\nnode server.js\n\n# Start React frontend (in another terminal)\nnpm start\n# Open http://localhost:3000\n```\n
